## 1. Decisión cromática propuesta

La foto entregada corresponde al letrero de **Skot Burger**. El repositorio contiene además [`public/logo-burger.png`](../../../public/logo-burger.png), [`public/logo-acai.png`](../../../public/logo-acai.png) y [`public/logo-skot.png`](../../../public/logo-skot.png). Por ello propongo **tokens compartidos con acento contextual**, sin aplicar el rojo de Burger a las pantallas de Açaí ni a todos los estados del ERP. Los valores vivos extraídos del PNG de Burger son aproximadamente rojo `#F21924` y amarillo `#FEDA16`; la fotografía está afectada por luz y no se toma como manual de marca exacto.

| Uso | Token propuesto | HEX | Criterio |
|---|---|---|---|
| ERP · acción y navegación | `--brand-admin` | `#54294F` | Ciruela sobrio relacionado con el logo general. |
| POS Burger · acción | `--brand-burger` | `#A6262B` | Rojo del logo oscurecido para botones y texto legible. |
| POS Açaí · acción | `--brand-acai` | `#632A62` | Morado del negocio en controles, sin colorear todo el fondo. |
| Acento compartido | `--brand-gold` | `#E1B528` | Amarillo para líneas, indicadores y pequeños acentos; sin texto blanco. |
| Fondo / superficie | `--background` / `--surface` | `#F4F2F0` / `#FFFFFF` | Lectura prolongada y separación de tareas. |
| Texto / secundario | `--foreground` / `--muted` | `#2D2528` / `#5D5358` | Neutros cálidos. |
| Éxito / aviso / error / info | Tokens semánticos | `#1E6849` / `#805208` / `#A52D2D` / `#1F5F80` | Conservan su significado; el estado no depende solo del tono de marca. |

Contraste calculado: blanco/Burger `7,16:1`, blanco/Açaí `10,30:1`, blanco/ERP `11,62:1`, texto/fondo `13,37:1`, secundario/blanco `7,38:1`, texto oscuro/amarillo `7,71:1`. Blanco/amarillo es `1,94:1` y **no se usará**. El rojo vivo del logo/blanco es `4,25:1`: queda reservado al arte de marca; los controles usan el rojo oscuro. Estas parejas verifican la pauta de texto normal de [WCAG 2.2 AA, 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum) para la propuesta, no constituyen una certificación de todas las futuras pantallas.

**Precaución semántica:** el rojo de acción Burger se parece al rojo de error. Las acciones destructivas deberán mostrar texto e icono explícitos y, cuando corresponda, confirmación; nunca se identificarán solo por color. El borde todavía necesita una pareja de contraste funcional medida en contexto; el HEX no se elige por herencia del prototipo.

## 2. Alcance técnico

Se conserva Next.js 14 App Router, React 18, TypeScript, Tailwind CSS 3, CSS personalizado, Lucide React y las fuentes Lexend/Source Sans 3 ya incluidas en los prototipos. `next/font/local` está disponible en [Next.js 14](https://nextjs.org/docs/14/app/building-your-application/optimizing/fonts); `theme.extend` permite incorporar tokens a [Tailwind CSS 3](https://v3.tailwindcss.com/docs/theme). No se propone instalar dependencias ni migrar versiones.

El estado funcional actual se mantiene: `src/app/page.tsx` filtra módulos mediante `showWhen`; `src/app/(pos)/burgers/page.tsx` conserva `useBurgerSale`, combos, descuentos, pagos, impresión y cola offline; `src/app/(pos)/acai/page.tsx` conserva `useAcaiSale`, `useScale`, balanza y sincronización. Los prototipos no sustituyen a esas fuentes de datos.

### 2.1. Tema contextual y límites de responsabilidad

- **Un sistema, tres contextos.** Mantener tokens semánticos de superficie, texto, borde, estado, espaciado, radio, sombra y tipografía comunes. Definir `--brand-primary`, `--brand-secondary`, `--brand-accent`, `--background`, `--surface`, `--foreground`, `--muted`, `--border`, `--success`, `--warning`, `--error` y `--info`. Mapear `--brand-primary` a `#54294F` (admin), `#A6262B` (Burger) o `#632A62` (Açaí); acento compartido `#E1B528`. No crear copias cromáticas de componentes ni HEX sueltos en páginas migradas.
- **Selección del contexto.** Aplicar un atributo estático `data-brand="admin|burger|acai"` al contenedor de experiencia apropiado, no al usuario ni al objeto de venta. El dashboard y módulos administrativos usan `admin`; `/burgers` usa `burger`; `/acai` usa `acai`. La ruta identifica la experiencia visual, pero **no concede permiso ni elige sucursal**. Mantener el atributo estable durante SSR/hidratación; el layout raíz puede permanecer neutro y servidor. Evitar derivar el tema desde `navigator`, `localStorage` o una condición de negocio en render inicial.
- **Sucursal y autorización.** `SessionProvider` obtiene `/api/auth/me`, que entrega `role`, `branchIds` y `branchTypes`; los POS actuales usan `branchIds[0]`. El usuario puede tener varias sucursales, por lo que `branchTypes` no mapea de forma inequívoca un `branchId` concreto al tipo. En Fase 3 se conserva la selección efectiva y se registra esta limitación; no se cambia para resolver un color. Middleware protege por rol ciertas páginas/APIs y `requireBranchAccess` valida sucursal en endpoints. El tema jamás determina acceso, filtros de datos o reglas comerciales.
- **Tailwind 3.** Extender `theme.extend.colors` con referencias a CSS Custom Properties y nombres semánticos; declarar clases completas y detectables en los archivos bajo `src` (el `content` actual no escanea prototipos). Evitar interpolar nombres de clase en runtime. Fijar mapa de variantes de Button/Badge y tokens de foco/sombra; revisar la combinación PostCSS existente antes de tocarla, sin migrar Tailwind.
- **Next App Router.** Mantener `src/app/layout.tsx` como Server Component y `SessionProvider` como frontera cliente. Crear layouts anidados solo si reducen duplicación real y no cambian rutas, orden de providers o render inicial; no asumir que ya existen. Cargar fuentes locales mediante la capacidad de Next 14 cuando se implemente, conservando licencias y un fallback estable. Componentes estáticos y navegación sin estado pueden permanecer en servidor; interacciones de POS, búsqueda, diálogo y sesión quedan en fronteras cliente pequeñas. No importar código de `window`, balanza, IndexedDB ni `localStorage` al servidor.

### 2.2. Reutilización y estrategia de CSS

Primero catalogar consumidores y adaptar `searchable-select`, `image-upload`, `offline-banner`, `notification-bell`, `CashGate`, `product-grid`, `cart`, `modifier-modal` y `payment-modal` cuando corresponda. Crear solo la primitiva que tenga al menos dos usos claros o un contrato accesible que convenga centralizar. Prioridad: Button/IconButton, campos con etiqueta y error, Badge/StatusIndicator, Card, Dialog y estados Empty/Loading/Error. Checkbox, Radio, Switch, Dropdown, Tabs, Tooltip, Table y Textarea se incorporan **cuando un flujo real los necesite**; no construir un catálogo de componentes sin consumidores.

Los componentes de presentación reciben props TypeScript de datos ya calculados, estado, `disabled` y callbacks. `useBurgerSale`, `useAcaiSale`, `useScale`, `CashGate`, `sync-manager`, APIs y cálculo de totales conservan la propiedad de sus reglas. Un adaptador de vista puede convertir formatos (por ejemplo, importe mostrado, `aria-label` o estado de balanza) sin recalcular precios ni inferir confirmación. React memoización y virtualización solo después de medir un cuello de botella con 3, 6, 20 y 100 productos; no encarecer el flujo normal.

El CSS actual combina `globals.css`, clases Tailwind con colores fijos, estilos inline en páginas y módulos CSS de balanza. Elaborar un mapa de selectores, colores y consumidores antes de migrar; introducir tokens en una capa de alcance controlado, mantener estilos antiguos hasta que cada consumidor pase sus pruebas y retirar reglas obsoletas por lote. Evitar `!important` y selectores globales nuevos sobre `button`, `input`, `dialog` o `table`. Revisar especificidad de estados `hover`, `focus-visible`, `disabled`, contraste de controles y el `theme-color` fijo del layout como tarea visual separada, sin alterar la política PWA. El plan de reversión conserva los estilos anteriores hasta terminar la migración de sus rutas.

### 2.3. Navegación y matriz de permisos a preservar

La navegación actual no tiene una única fuente: `src/app/page.tsx` define `ALL_MODULES.showWhen`; `src/app/admin/page.tsx` define sus secciones; `src/middleware.ts` contiene reglas de rutas, y las APIs usan además autorizaciones de servidor. La futura navegación debe derivar sus entradas de la política funcional **existente y verificada**, sin convertirla en autoridad de seguridad. Antes de compartir un menú, contrastar cada enlace y acción con el middleware y la API correspondiente.

| Rol | Accesos visibles hoy en `/` | Controles de URL directa y sucursal a probar |
|---|---|---|
| ADMIN | Administración, inventario, fábrica y gastos; POS no aparece por `showWhen` | `/admin` y `/factory` admitidos por middleware; `/burgers` y `/acai` carecen de regla de página específica: comprobar comportamiento real sin ampliar acceso ni asumir tipo de sucursal |
| MANAGER | POS Açaí/Burger solo si `branchTypes` incluye el tipo; caja, inventario y gastos | `/admin` y `/factory` admitidos por middleware aunque no figuran en `showWhen`; verificar acciones y APIs específicas antes de ofrecer enlaces |
| CASHIER | POS por tipo asignado, caja, inventario y gastos | `/admin` y `/factory` restringidos por middleware; probar `/burgers`, `/acai` y endpoints con una sucursal permitida y otra ajena |
| WAREHOUSE | Fábrica y gastos | `/factory` permitido; `/admin/alerts` permitido como excepción, `/admin` general restringido; inventario aparece en permisos de servidor pero no en el inicio: documentar antes de cambiar enlaces |

Esta matriz describe el código, **no una política aprobada nueva**. Incluir usuarios con 0, 1 y varias sucursales, tipos mixtos y sesión caducada; verificar visibilidad de acciones, navegación, `403/401` de APIs, acceso directo por URL y que ningún tema visual amplíe permisos. Las discrepancias se registran como hallazgos funcionales aparte. `src/middleware.ts`, `src/lib/branch-access.ts` y `src/lib/auth-middleware.ts` son referencias de lectura para la implementación visual, no archivos a modificar por este plan.

## 4. Protección funcional y pruebas

- **No tocar** APIs, Prisma, middleware, contratos de venta, reglas de permisos, `src/lib/sync-manager.ts`, `src/hooks/use-burger-sale.ts`, `src/hooks/use-acai-sale.ts`, `src/hooks/use-scale.ts` ni service worker para aplicar estilos. Si un estado visual requiere datos adicionales, comprobar primero si ya existen en las props.
- Validar ERP con usuarios de rol diferente; mantener exactamente la lógica `showWhen` del dashboard. No añadir KPI inventados.
- Validar Burger con 3, 6 y más de 20 productos, imágenes presentes/ausentes, combos, extras, descuentos, pedidos extensos, método de pago e impresión de comanda.
- Validar Açaí con balanza desconectada, conectada sin lectura, lectura inestable, lectura estable, peso confirmado, extras y cobro. La conectividad no equivale a estabilidad ni confirmación.
- En 375, 768, 1024 y 1440 px comprobar foco no oculto por el dock, sin desbordamiento y objetivos adecuados según [WCAG 2.2, 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum) y [2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum). Probar pedidos largos y textos reales.
- Probar venta online y offline con la cola existente, reintento de sincronización, impresión y cobro antes de dar por terminada la fase. No declarar conformidad WCAG completa solo con capturas.

### 4.1. Persistencia y estados verificables

La cola efectiva de ventas de ambos POS es `src/lib/sync-manager.ts`, clave `skot_offline_sales_queue` en `localStorage`, con estados por elemento `pending`, `syncing` y `failed`; emite `skot-offline-queue-updated`. `syncOfflineQueue()` devuelve `{total,synced,errors}` y elimina los elementos confirmados por la API. La API `/api/pos/sale` consulta `branchId + offlineId` para evitar duplicación de reintentos; la prueba debe comprobar su comportamiento con payload idéntico y no asumir garantía para payload distinto. Los catálogos POS también usan `localStorage` como caché (`pos-burgers-*`, `pos-acai-*`) y Açaí guarda `skot_scale_ip`.

Hay piezas adicionales basadas en IndexedDB (`src/hooks/use-sync-queue.ts`, `src/lib/sync-engine.ts`, `src/lib/query-client.ts`) y un service worker en `public/sw.js`. La búsqueda de importaciones actual no muestra `QueryClientProvider` ni consumidores de `syncEngine`; `offline-banner.tsx` sí importa `useSyncQueue`, pero no se observó montado en las rutas inspeccionadas. **No presentar esas piezas como cola de ventas POS ni conectarlas por el rediseño.** El service worker aplica `network first` a documentos GET y no intercepta `/api/`; tampoco garantiza por sí mismo venta offline.

| Estado visual | Evidencia mínima permitida | Precaución |
|---|---|---|
| Con conexión / sin conexión | `useNetworkStatus` o `navigator.onLine`, más resultado de petición si se necesita confirmar alcance del servidor | “Con conexión” describe red del navegador; no promete acceso a API |
| Ventas pendientes | Longitud y `status` de `getOfflineQueue()`; actualizar por evento y recarga | Pendientes no implica que el dispositivo esté sin conexión |
| Sincronización en curso | `isSyncing` del flujo o elementos `syncing` de la cola | Deshabilitar reintento simultáneo sin modificar la política de sincronización |
| Sincronización completada | Resultado inmediato de `syncOfflineQueue()` con ventas confirmadas; mensaje transitorio | Cola vacía al iniciar la página no prueba que se haya sincronizado ahora |
| Error de sincronización | `errors` o elementos `failed` y mensaje disponible | Conservar detalle útil sin exponer datos sensibles |

Matriz controlada de pruebas: venta online; venta offline con cola; pérdida de red durante solicitud; recuperación de red; varias ventas pendientes; reintento después de fallo; mismo `offlineId` reenviado para revisar idempotencia observable; recarga antes y después de sincronizar. Usar mocks o base aislada y verificar que ningún escenario cree ventas reales. Registrar antes/después de cola, payload, respuesta y aviso visible. Limpiar únicamente datos de prueba del contexto aislado. Si el ambiente no permite probar balanza/impresora real, marcar esa verificación como pendiente, sin declarar la etapa completa.

### 4.3. Matriz de riesgos y diagnóstico

| Riesgo observado o plausible | Impacto | Probabilidad | Control y evidencia de cierre |
|---|---|---|---|
| Diferencia monetaria o peso por traslado de cálculo al componente | Crítico | Media | Totales/payload contra línea base con casos Burger y Açaí; hooks comerciales intactos |
| Acceso visible o URL directa inconsistente con roles/sucursal | Crítico | Alta: ya hay divergencias entre inicio y middleware | Matriz de cuatro roles y sucursales; registrar discrepancias sin ampliar permisos |
| Venta offline perdida, estado falso o reintento duplicado | Crítico | Media | Cola `localStorage` y respuesta API en pruebas aisladas; recarga y mismo `offlineId` |
| Error al distinguir lectura estable de peso confirmado | Crítico | Media | Estado y acción vinculados a campos reales; prueba de espera/estable/confirmado |
| CSS nuevo afecta formularios y módulos antiguos | Alto | Alta | Alcance por contexto, inventario de selectores, capturas y reversión por lote |
| Dock o diálogo tapa acciones/foco en 375 px | Alto | Media | Playwright y revisión manual con pedido largo, teclado virtual y safe area |
| Demasiado JS o re-render de catálogo en POS | Alto | Media | Línea base de bundle y latencia 3/6/20/100; optimización solo con perfil |
| Fuente o imagen causa salto de layout | Medio | Media | `next/font/local`, dimensiones reservadas y medición de CLS |
| Mensajes de error/impresión/pago sustituidos por aviso genérico | Alto | Media | Casos de fallo reproducidos; texto de recuperación útil y sin datos sensibles |

La probabilidad es una estimación para priorizar el plan, no una medición de incidentes. Cualquier cambio que requiera resolver la divergencia de permisos, la diferencia de umbrales de peso u otra regla comercial sale del alcance visual y necesita una decisión funcional separada.
